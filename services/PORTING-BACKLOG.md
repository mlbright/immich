## machine-learning (cpu variant)

Ported: `/`, `/ping`, `/predict` for CLIP (visual, textual, M-CLIP), facial recognition and OCR with `MACHINE_LEARNING_MODEL_REVISION` `main` or `v2`. Checked by `mise //services:ml-differential`: 90 checks, 0 failures, with 78 byte-identical on `main` and 80 on `v2`.

- [x] CPU graph preparation (`sessions/prepare.py`): the prepared `model.onnx`, `model.data` and `manifest.json` are byte-identical to Python's, so either service loads what the other prepared. With all six default models loaded on an M-series Mac, Rust's physical footprint is 478 MB after preload and 1,044 MB after the differential run, against 633 MB and 1,304 MB for Python's three processes.
- [x] Model revision `v2` on CPU: `immich_model` 0.2.0's CPU rewrite plan (`skip_layer_norm`) and its digest, with `onnxscript`'s `FuseSkipLayerNorm` rule and the `onnx_ir` passes it runs ported in `onnx_ir.rs` and `immich_model/`. The rewritten graphs are byte-identical to Python's on 140 v2 graphs (every CLIP and OCR model, 4,002 fusions), and a v2 cache prepared by Rust is byte-identical to Python's, `refs/<revision>` included. `mise //services:ml-differential` against a v2 Python service: 75 checks, 65 byte-identical, 0 failures. Still Python-only, as neither applies on CPU: the other hardware targets' rewrites (each registry row without a transform fails when planned) and fp16 derivation, and CLIP text graphs that leave their token table to the host (`embedding` metadata), which only the RKNPU rewrite produces.
- [x] JPEG XL decoding: `pillow_jxl.rs` ports `pillow-jxl-plugin` 1.3.8 on the same `jpegxl-rs` 0.15.0 and vendored libjxl 0.12.0, followed by Pillow's conversions to RGB. Pixel-identical to Python on 82 files covering lossy and lossless, RGB, RGBA, gray, gray with alpha, 16-bit, float and recompressed JPEG; a truncated file fails with the same message. `jpegxl-rs` is GPL-3.0-or-later, as is upstream's plugin.
- [x] Concurrent requests to one model run at once, as in Python: `OrtGraph::infer` calls ONNX Runtime's `Run` through the C API, which ONNX Runtime documents as safe from several threads, because the `ort` crate's `Session::run` takes `&mut self`. At 16 requests in flight on an M-series Mac, Rust and Python serve the same rate for CLIP (151 req/s), text (320 req/s) and faces (36 req/s). Like Python, each concurrent run keeps its own buffers in ONNX Runtime's arena: after 16-way load the footprint was 4.5 GB for Rust against 5.1 GB for Python.
- [x] OCR speed: one request at a time, the 13 test images take 2,064 ms against Python's 2,061 ms (2,493 ms before), and 42 against 39 req/s at 16 in flight. The Pillow and NumPy ports in `pil.rs` and `numpy.rs` stay byte-identical to Pillow 13 and NumPy on 465 generated cases, and are now faster than Pillow for the detection resize (36 ms against 78 ms for a 6000×4000 photo).
- [x] `Resampling::Nearest` resizes: ported from Pillow's `ImagingScaleAffine`, which steps through source positions by repeated addition rather than multiplication. Byte-identical to Pillow 13 on 454 generated cases, where it differed on 8 of 54 before. Only a CLIP model whose `preprocess_cfg.json` asks for `nearest` interpolation reaches it.
- [x] Process model (gunicorn and uvicorn): `gunicorn.rs` binds the socket and runs `MACHINE_LEARNING_WORKERS` copies of the binary as `immich-ml worker` on it, handing out `MACHINE_LEARNING_DEVICE_IDS` in turn. It replaces workers that exit, stops with exit code 3 when one fails to boot, aborts then kills a worker whose heartbeat is older than `MACHINE_LEARNING_WORKER_TIMEOUT`, and gives workers 10 s on SIGTERM. Workers close idle keep-alive connections after `MACHINE_LEARNING_HTTP_KEEPALIVE_TIMEOUT_S`; hyper's header timeout also closes a new connection that sends nothing for that long, which uvicorn leaves open. After `MACHINE_LEARNING_MODEL_TTL` without requests a worker exits and a fresh one boots, preloading again: with the arena off and all six models preloaded, a burst's 2.4 GB returns to 246 MB (Python: 2.2 GB to 545 MB).
- [x] FastAPI's `/openapi.json`, `/docs`, `/docs/oauth2-redirect` and `/redoc`: `fastapi.rs` serves them byte-identical to FastAPI 0.162.0. FastAPI renders them the same for every request here, because uvicorn's `root_path` is always empty, so the files under `src/fastapi/` are copies of its output. The routing around them is ported too. `/ping/` and any other path that matches a route without its trailing slashes gets Starlette's 307 to that route, built from the `Host` header, with the scheme from `X-Forwarded-Proto` when the client is in `FORWARDED_ALLOW_IPS` (validated as gunicorn does). Request paths are percent-decoded before routing, as uvicorn does. HEAD is answered on the docs pages but is a 405 on `/` and `/ping`, as FastAPI does. 54 raw requests compared with Python give identical status, headers and body; 15 of them are now in `mise //services:ml-differential`.
- [x] mimalloc as the allocator, as in the Python image: the `mimalloc` crate with `override` replaces `malloc` for the whole process, ONNX Runtime and OpenCV included, as `/etc/ld.so.preload` does upstream, and `allocator::release` calls `mi_collect(true)`. The crate bundles mimalloc 3.3.2; the upstream image takes whatever Debian trixie-backports carries when it is built (3.5.3 now). With `MACHINE_LEARNING_MODEL_ARENA=false`, as the CPU image sets, on an M-series Mac with all six default models: 242 MB after preload against 390 MB with the system allocator, the same throughput, and about 1.4 GB held after a 16-way burst against about 1.0 GB, because idle threads never purge the pages they freed. `MIMALLOC_PURGE_DELAY=0` brings that down to 370 MB; the upstream image leaves mimalloc at its defaults.
- [ ] Container image for the `cpu` variant, with OpenCV 4.14 and libjpeg-turbo, and `MACHINE_LEARNING_MODEL_ARENA=false` as the upstream CPU image sets.

Accepted differences:

- ONNX Runtime is the build `ort` downloads, linked statically. Its kernels are about 10% slower than Microsoft's build of the same commit (402979a): the OCR recognition graph takes 4.20 ms against 3.81 ms at width 160 on an M-series Mac, with the same Rust code loading either library. Profiles show the same kernels in the same proportions, but the downloaded build spins less in its thread pool (1% of busy time against 8%). Whole OCR requests still run at Python's speed. Building ONNX Runtime from source as a static library, or shipping Microsoft's library next to the binary, would close the gap.
- Responses carry no `server: uvicorn` header; nothing in Immich reads it.
- OCR crops come from a float32 8×8 solve whose last bits depend on the platform's LAPACK; on rare near-ties one character differs.
